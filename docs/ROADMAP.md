# meddata-gen 市场分析与开发迭代规划

> 生成日期：2026-05-20
> 用途：后续版本迭代的参考备忘

---

## 一、项目现状速览

meddata-gen 目前已具备的核心能力：

| 维度 | 现状 |
|------|------|
| 覆盖系统 | 7 个（HIS/EMR/LIS/RIS/ECG/ICU/病案） |
| 数据库架构 | 多库独立（his_db/emr_db/...），模拟真实医院数据孤岛 |
| 生成模式 | Legacy（按表独立）+ Event（事件驱动就诊旅程） |
| 数据质量 | 随机缺陷 + 5 种场景化缺陷（系统升级 outage、接口切换、时钟漂移等） |
| 临床一致性 | 疾病画像绑定、科室匹配、就诊率、检验异常模式 |
| 输出格式 | PostgreSQL、CSV、FHIR R4 Bundle |
| 字典管理 | 8 张字典表 + Excel 模板导入/导出 + 内置示例 |
| 规则引擎 | 患者-疾病匹配、科室匹配、就诊率、混合绑定模型 |

## 二、市场定位与竞争格局

### 2.1 国际市场竞品

| 工具 | 定位 | 与 meddata-gen 的差异 |
|------|------|----------------------|
| [Synthea](https://synthetichealth.github.io/synthea/) | 美国 HHS 支持，全球医疗合成数据标杆 | 面向美国医疗体系，输出 FHIR/OMOP/CDA，不模拟中国 HIS 多库架构 |
| [simhospital](https://github.com/google/simhospital) | Google 出品，HL7v2 消息流模拟 | 侧重消息流和 ADT 事件，不生成关系型数据库测试数据 |
| [DATAMIMIC CE](https://github.com/rapiddweller/datamimic) | 通用合成数据引擎，含医疗 domain | 通用型工具，缺乏中国 HIS 业务深度（如病案、医保、DRG） |
| Eunomia / omock | OMOP CDM 测试数据集 | 面向科研分析（OHDSI 生态），非 ETL 测试 |

### 2.2 国内市场空白

根据中国医院协会信息专业委员会（CHIMA）和搜索调研，**国内几乎没有开源的、专门针对中国三甲医院多系统架构的模拟数据生成器**。

现有解决方案的痛点：
- HIS 厂商（东软、卫宁、创业慧康等）各自维护内部测试数据集，不对外
- 医院信息科做 ETL 测试时，通常手动脱敏真实数据，效率低且合规风险高
- 数据治理/互联互通测评项目缺乏"脏数据"来验证清洗规则
- 医疗 AI 公司需要大量标注数据，但真实数据获取门槛极高

### 2.3 meddata-gen 的差异化定位

```
国际市场：Synthea 主导 FHIR/OMOP 科研生态
国内市场：空白 —— meddata-gen 几乎无直接竞品

meddata-gen 独特价值：
1. 中国三甲医院业务模型（病案首页、医保结算、DRG）
2. 7 系统多库架构，模拟真实数据孤岛和跨系统关联断裂
3. 场景化缺陷注入（模拟真实业务根因，非随机噪声）
4. 事件驱动的临床一致性（就诊旅程 -> 多系统数据天然对齐）
5. 支持 FHIR 输出，兼顾国内应用和国际标准对接
```

## 三、目标用户与使用场景

### 3.1 核心用户画像

| 用户群体 | 规模估算 | 核心痛点 | 付费意愿 |
|---------|---------|---------|---------|
| **HIS/医疗信息化厂商** | 国内约 200+ 家 | 测试环境数据准备耗时，跨系统联调困难 | 中（作为开发工具） |
| **医院信息科/数据治理团队** | 三级医院 ~3000 家 | ETL 测试缺脏数据，互联互通测评准备 | 中高（项目预算内） |
| **医疗大数据平台开发商** | 数十家 | 需要可重复的测试数据集验证平台功能 | 高 |
| **医疗 AI 公司** | 数百家 | 算法训练/验证需要大量结构化医疗数据 | 高（数据获取成本极高） |
| **高校/培训机构** | 数百家 | 教学演示缺乏真实感的数据库环境 | 中低 |

### 3.2 高价值使用场景

1. **ETL/数据治理项目测试**
   - 模拟跨 7 系统的数据抽取、清洗、关联
   - 验证缺失值处理、主键冲突、时间窗口对齐等规则
   - 场景化缺陷可模拟真实生产事故（如 LIS 升级期间数据批量缺失）

2. **互联互通测评 / 电子病历评级准备**
   - 生成符合测评标准的数据量（门诊/住院人次、检验检查量）
   - 验证数据标准化和接口对接

3. **CDR（临床数据中心）建设验证**
   - 多源数据融合测试
   - 患者主索引（EMPI）匹配算法验证

4. **医疗 AI 算法开发**
   - 疾病预测模型需要带标签的时序临床数据
   - 罕见病算法需要人为构造特定病例分布

5. **信创迁移测试**
   - 国产数据库（达梦、人大金仓、OceanBase）兼容性测试
   - 验证从 Oracle/SQL Server 到国产库的 ETL 流程

## 四、商业价值评估

### 4.1 开源 + 商业化路径

| 模式 | 可行性 | 说明 |
|------|--------|------|
| **完全开源（MIT）** | 当前状态 | 建立社区影响力，吸引贡献者 |
| **企业版 / SaaS** | 高 | 云端一键生成 + 更多系统模板 + 可视化配置 |
| **垂直场景增值包** | 高 | 医保结算测试包、DRG 分组验证包、互联互通测评包 |
| **培训 + 咨询** | 中 | 基于工具的医疗数据治理培训 |

### 4.2 关键成功因素

1. **数据真实性** — 疾病画像、临床规则越精细，数据越像"真的"
2. **扩展性** — 能否快速适配不同 HIS 厂商的数据结构
3. **易用性** — CLI 对技术人员友好，但企业用户需要 GUI
4. **社区生态** — 能否形成字典模板、缺陷场景的共享社区

## 五、开发迭代路线图

基于市场分析，建议分 **4 个阶段**推进，每个阶段 2-3 个月：

### Phase 1：夯实基础（v0.2.0）-- 2 个月

**目标：让工具从"能用"变成"好用"，降低上手门槛**

| 优先级 | 功能 | 价值 |
|--------|------|------|
| P0 | **Docker Compose 一键启动**（PostgreSQL + 工具） | 消除环境配置门槛，这是目前最大的使用障碍 |
| P0 | **配置外部化**（YAML/JSON 配置文件替代硬编码 config.py） | 支持不同医院场景的自定义配置 |
| P0 | **增量生成**（基于时间窗口追加数据，不覆盖历史） | 模拟真实业务的增量 ETL 场景 |
| P1 | **数据量验证增强**（跨系统关联率可视化报告） | 让用户直观看到数据质量指标 |
| P1 | **更多内置疾病画像**（从 10 种扩展到 50 种） | 提升数据多样性和真实感 |

### Phase 2：扩展覆盖（v0.3.0）-- 2 个月

**目标：覆盖更多医疗子系统和业务场景**

| 优先级 | 功能 | 价值 |
|--------|------|------|
| P0 | **医保结算系统（mi_db）** | 医保控费、DRG/DIP 是当前医院最大痛点 |
| P0 | **药品供应链（pharmacy_db）** | 药占比、集采、SPD 管理场景 |
| P0 | **手术麻醉系统（anes_db）** | 手术排程、麻醉记录、PACU |
| P1 | **门诊处方详情扩展**（中草药、配伍禁忌） | 提升中医/中西医结合场景覆盖 |
| P1 | **体检系统（pe_db）** | 健康体检中心数据模拟 |

### Phase 3：企业级能力（v0.4.0）-- 3 个月

**目标：从开发工具升级为数据治理平台组件**

| 优先级 | 功能 | 价值 |
|--------|------|------|
| P0 | **Web UI 配置界面**（Streamlit/FastAPI + Vue） | 非技术用户（信息科）可用 |
| P0 | **自定义 Schema 映射**（适配不同 HIS 厂商表结构） | 解决"每家医院表结构不同"的核心痛点 |
| P0 | **多数据库支持**（MySQL、达梦、人大金仓、OceanBase） | 信创场景刚需 |
| P1 | **数据血缘追踪**（生成数据字典，标注每字段的来源规则） | 数据治理团队需要 |
| P1 | **Grafana 监控面板模板**（数据量、质量指标实时看板） | 与现有运维体系集成 |
| P1 | **OMOP CDM 输出** | 对接国际科研生态，扩展海外用户 |

### Phase 4：智能化与生态（v0.5.0+）-- 3 个月

**目标：从"数据生成器"进化为"医疗数据模拟平台"**

| 优先级 | 功能 | 价值 |
|--------|------|------|
| P0 | **LLM 驱动的病历内容生成**（基于疾病画像生成结构化+自由文本病历） | 目前 EMR 病历内容过于模板化，LLM 可大幅提升真实感 |
| P0 | **社区字典市场**（用户上传/下载不同地区的字典模板） | 形成生态壁垒 |
| P0 | **场景模板市场**（预置"新院区开业"、"疫情爆发"、"系统升级"等场景） | 一键生成特定业务场景的数据 |
| P1 | **压力测试模式**（模拟高并发写入，测试数据库性能） | 性能测试场景 |
| P1 | **数据脱敏/反脱敏对照**（生成与真实数据分布一致的合成数据） | 满足更严格的隐私合规要求 |

## 六、近期（Phase 1）开发任务分解

```
Phase 1: v0.2.0 -- 夯实基础（建议 6-8 周）

Week 1-2: Docker & 配置
  - docker-compose.yml（PostgreSQL 14 + 初始化脚本）
  - 配置加载系统：CLI --config file.yaml
  - 环境变量覆盖配置项

Week 3-4: 增量生成 & 数据质量报告
  - --incremental --since 2024-01-01 参数支持
  - verify 命令输出 HTML/JSON 质量报告
  - 跨系统关联率可视化（如 his.patient_id <-> emr.patient_id
    匹配率 92%，缺失 8% 的明细）

Week 5-6: 疾病画像扩展 & 字典完善
  - 疾病画像从 10 -> 50 种（覆盖内外妇儿常见疾病）
  - 检验项目异常模式细化（如心梗的肌钙蛋白动态变化）
  - 手术字典与疾病画像绑定（如骨折 -> 内固定术概率）

Week 7-8: 文档 & 社区建设
  - 完整用户文档（安装、配置、自定义扩展指南）
  - 示例场景教程（"模拟一次肺炎住院全程"）
  - GitHub Actions CI/CD（自动测试、发布）
```

## 七、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **HIS 厂商数据格式差异大** | 高 | 优先做 Schema 映射配置层，不做硬编码适配 |
| **真实临床知识不足** | 中 | 与医院信息科合作验证，引入医学顾问 |
| **Synthea 等工具本地化竞争** | 低 | Synthea 不擅长多库关系型场景，专注差异化 |
| **开源社区活跃度不足** | 中 | Phase 1 解决上手门槛，Phase 3 推出 Web UI 扩大用户群 |
| **信创数据库兼容性复杂** | 中 | 通过 SQLAlchemy 或方言层抽象，逐步适配 |

## 八、结论

meddata-gen 处于一个**竞争稀疏但需求旺盛**的市场区间：

- **国内无直接开源竞品**，先发优势明显
- 医疗数据隐私合规趋严，合成数据是刚需
- 医院信创改造、互联互通测评、DRG/DIP 改革都在创造新的测试数据需求

**建议立即启动 Phase 1（Docker + 配置外部化 + 增量生成）**，这三项是降低用户使用门槛、扩大社区影响力的关键。同时可以开始与 1-2 家医院信息科或 HIS 厂商建立合作，用真实需求驱动 Phase 2 的系统扩展方向。
